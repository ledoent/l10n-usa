Payment Provider: Zift

Adds Zift as a payment provider, so customers can pay invoices and orders by card or by ACH bank transfer.

Zift exposes a single form-encoded gateway endpoint where a requestType field selects the operation. This module implements the direct (inline) flow: the payment details are tokenized in the browser and the server charges the token, so no card number or bank account number ever reaches Odoo.

Both methods are supported and they behave differently on purpose:

  • Card — an approval is an issuer guaranteeing the funds, so the payment is confirmed immediately. Manual capture is available.
  • ACH direct debit — an accepted debit has only entered the ACH network. It settles in one to three business days and can be returned after that, so the transaction is recorded as pending and the invoice is not reconciled until settlement is confirmed.

Tokenization uses Zift’s account-verification, a genuine $0 operation that places no hold on the customer’s account and returns a durable token. For bank accounts it runs with verificationMode=PF, so a failed verification declines the tokenization rather than storing an account that cannot be debited.

Configuration

Go to Invoicing → Configuration → Payment Providers, open Zift, and fill in the three credentials Zift issues for the merchant account:

  • User Name
  • Password
  • Account ID

All three travel in the body of every request. Leave Live Mode disabled until they have been proven against the sandbox. Odoo 20 uses is_live, not the older provider State selector: sandbox traffic goes to sandbox-secure.zift.io, and live traffic goes to secure.zift.io.

Zift settles in USD only, and ACH Direct Debit is restricted to the United States and Puerto Rico.

PCI scope — read before enabling this in production

Zift documents two ways to collect a card and neither is an iframe:

  1. Hosted Payment Pages — a redirect to Zift’s own page.
  2. proxynization.js — in Zift’s words, “create your own payment page and utilize our proxynization API to help reduce your PCI scope”.

This module implements the second. The card and bank fields are rendered on the Odoo payment page and read by a script served into that page. No card number or account number reaches an Odoo server — but under the PCI SSC’s own division, what decides the Self-Assessment Questionnaire is whose code runs on the capture page, not where the data is posted. A redirect or a third-party iframe is SAQ A eligible; a merchant script or Direct Post implementation is SAQ A-EP, which carries roughly 140–190 requirements against SAQ A’s twenty-odd, plus quarterly ASV scanning.

Zift’s claim to “reduce PCI scope” is accurate. It is a different claim from SAQ A eligibility. Choosing this module over the redirect is a compliance decision for whoever signs the attestation. Nobody who wrote this module is a QSA, and nothing here is compliance advice.

ACH behaves differently from card, by design

An accepted ACH debit is recorded as pending, not confirmed, and the invoice is left unreconciled. That is correct: the debit has entered the ACH network and settles in one to three business days, and it can be returned after that.

Nothing currently resolves a pending debit automatically. Zift sends asynchronous settlement notifications, but how it authenticates a callback is not published, so this module ships no notification endpoint (see ROADMAP). Until that is answered, ACH payments must be confirmed against the bank by a person. Plan for that before enabling ACH, or enable card only.

Optional payer processing-fee pass-through

The setting Pass gateway processing fees to the payer is disabled by default. Enable it only for a Zift merchant profile configured to collect and retain its convenience fee separately from the merchant’s payment principal. This implementation adds no merchant-defined markup or fee income.

For interactive card and ACH payments, including saved methods, Odoo requests requestType=convenience-fee using the tokenized instrument and principal in cents. The payer sees principal, fee and total and must choose Accept fee and pay. Cancel sends no financial request. Quotes expire after ten minutes and are bound to the payer, instrument, merchant profile, currency and amount. Changed inputs require a new quote. Validation transactions do not incur fees. Off-session charging cannot bypass acceptance; fee mode requires automatic capture. Keep fee mode disabled for charge-on-ship/manual-capture profiles.

The sale sends principal as amount and the accepted fee separately as feeAmount. Transaction and invoice amounts stay at principal; the gateway’s retained fee does not become merchant revenue or tenant credit. This requires account_payment so native invoice settlement uses the original principal. Accepted amounts and time are retained on the transaction and payment status. ACH acceptance remains pending; fee acceptance is not settlement confirmation.

Odoo refunds send a positive principal amount with feeAmount=0. Gateway fee refunds require separate handling under the actual merchant policy; this is not a statement that fees are legally nonrefundable. A timeout, incomplete response or principal/fee/instrument mismatch leaves an error requiring gateway inquiry; Odoo will not automatically retry a consumed quote. A database failure around an external request still requires reconciliation, not blind resubmission.

Protocol basis: Zift’s Convenience Fee integration notes and fee policy fields. This is the additional convenience-fee model, distinct from a service fee withheld out of a remitted total. Merchant-profile eligibility, ACH/card permissions, exact response amount semantics, fee refunds and settlement must be verified with issued sandbox credentials before enabling this option in production. All local acceptance traffic uses synthetic mocked responses.

Usage

Once the provider is enabled, Zift appears as a payment option wherever Odoo offers one — the customer portal’s Pay Now on an invoice, the eCommerce checkout, and a payment link.

The customer chooses Card or ACH Direct Debit and fills the fields inline. Saving the method for later is offered when Allow Saving Payment Methods is enabled on the provider; storing one runs Zift’s $0 account-verification, which places no hold.

What to expect afterwards:

Method Transaction state Invoice
Card Confirmed (or Authorized if manual capture is on) Reconciled
ACH Direct Debit Pending Not reconciled

A pending ACH transaction is not a failure and should not be retried. The debit has been accepted into the ACH network and takes one to three business days to settle. Confirm it against the bank before treating the invoice as paid — see CONFIGURE for why this is manual today.

Refunds are issued from the transaction, full or partial, and go through Zift’s credit operation. Cards additionally support a manual capture of a prior authorisation, and voiding one before settlement.

Known issues / Roadmap

These are gaps in Zift’s published documentation, not decisions deferred for convenience. Each one is a thing this module declines to invent.

  • No notification endpoint. Zift sends asynchronous notifications for ACH settlements, returns, and Notices of Change — the NACHA C01–C06 corrections that replace a stored account’s token, routing number, holder name or account type. Handling them needs an HTTP endpoint, and an endpoint that rewrites stored payment credentials has to authenticate its caller. How Zift signs or authenticates a callback is not in the public documentation, so the route is absent rather than guessed at.
  • ACH settlement is therefore manual. A pending debit stays pending until somebody confirms it against the bank. Resolving it automatically depends on the point above.
  • Response-code semantics are coarse. Which responseCode values are an acceptance, a soft decline and a hard decline is not documented. Anything this module does not recognise is treated as an error, which is safe and blunt: a retryable decline currently looks the same as a permanent one.
  • No Level II / Level III data for cards. The mapping is well understood and deliberately omitted here. commodityCode is String(4) and acquirer-designated, and nothing says which values a given acquirer expects — an unrecognised code can fail the record outright, where an absent optional field simply degrades. Sending it needs an answer from the acquirer first.
  • The buyer’s PO number has no obvious home. Zift’s orderCode is the merchant’s identifier, which this module fills with the transaction reference. The number a purchasing-card holder reconciles against is the buyer’s own PO, and no published field is clearly for it.
  • Untested against the live gateway. Every test here runs against mocked responses. Nothing has been proven against Zift because no sandbox credential has been issued; the gateway rejects on credentials and nothing else, so the whole integration is provable the day one arrives.
  • Fee-profile acceptance is pending. Optional fee pass-through now has synthetic acceptance tests for explicit payer consent, principal-only invoice settlement, pending ACH, refunds and uncertain outcomes. Issued sandbox credentials and the intended merchant profile are still required to verify actual quote/sale/refund responses. Custom merchant markup, fee-mode manual capture and off-session fee charging are not implemented.
